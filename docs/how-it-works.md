# 工作流程

## 一次报障的经过

1. **发起**。用户发 `/debug`，插件记下是谁、在哪个群或私信里发起的，然后等这个人上传日志。别人在群里传的文件不算。
2. **收日志**。插件只看文件的扩展名（`.zip` / `.log`）、大小和下载地址，不打开文件，原样传到 CNB 作为 Issue 附件。
3. **开 Issue**。Issue 正文里有附件链接、文件类型和大小，以及一个内部追踪编号。标题用 `/debug` 后面的描述，没写描述时用 `[Debug] 日志分析`。
4. **请 NPC 分析**。插件在 Issue 下发一条评论 @NPC，要求它按“一句话描述 / 详细分析”两部分回复，并带上本轮专属的标记。评论内容和匹配规则见 [接口说明](api.md#npc-触发与回复匹配)。
5. **等回复**。插件定时拉取 Issue 评论，找到符合条件的 NPC 回复为止。
6. **发结果**。完整分析放在一条 QQ 合并转发里，随后再发一条普通消息，内容是一句话结论和下一步选项。
7. **确认**。用户发 `/debug resolve` 后，插件关闭 Issue，报障结束。

没解决的话，用户可以先补充信息（群里 @机器人，私信里直接发），再发 `/debug analyze`。插件会再 @ 一次 NPC，让它结合新评论重新分析，然后回到第 5 步。新结果发出后，确认时限重新计算。

同一个人在同一个群或私信里，同时只能有一个未结束的报障。

## 超时

| 阶段 | 默认时限 | 超时后 |
| --- | --- | --- |
| 等日志 | 10 分钟 | 报障结束，状态为“等待日志超时” |
| 等 NPC 回复 | 20 分钟 | 报障失败，Issue 保留 |
| 等用户确认 | 30 分钟 | 插件在 Issue 留言“报障人未确认，问题可能仍未解决”，然后关闭 Issue |

时限都能在配置里改，见 [配置说明](configuration.md#时间与大小)。

## 状态

| 状态 | 用户看到的 | 含义 |
| --- | --- | --- |
| `WAITING_LOG` | 等待上传日志 | |
| `PREPARING_LOG` | 正在提交日志 | 正在下载、暂存文件 |
| `CREATING_ISSUE` | 正在提交日志 | 正在上传附件、创建 Issue |
| `TRIGGERING_NPC` | 正在提交日志 | 正在发触发评论 |
| `WAITING_NPC` | 正在分析 | 等 NPC 回复 |
| `DELIVERING` | 正在发送分析结果 | 合并转发发送中，失败会退避重试 |
| `AWAITING_RECOVERY` | 等待你确认是否解决 | |
| `CLOSING_ISSUE` | 正在结束报障 | 关闭 Issue，失败会重试 |
| `UNCERTAIN` | 正在核对提交结果 / 需要管理员核对 | 见下一节 |
| `DONE` | 已完成 | |
| `EXPIRED` | 等待日志超时 | |
| `CANCELLED` | 已取消 | |
| `FAILED` | 处理失败 | |

`/debug status` 不会等后台轮询，而是当场把能推进的步骤都推进一遍。如果这时刚好查到 NPC 的回复，结果会立即发出来。

## 网络中断和重启

创建 Issue 和发触发评论这两个请求，如果中途断网或者插件重启，插件无法确定请求有没有成功。插件的原则是宁可停下来，也不重复提交：

- **触发评论**：插件去 Issue 里找内容完全相同的评论。找到了就接着等 NPC；在等待时限内一直没找到，就判定失败。用户看到的是“正在核对提交结果”，不需要做什么。
- **创建 Issue**：没有可靠的办法自动核对，插件会停在“需要管理员核对”，并给出完整的追踪编号。管理员拿这个编号去仓库里搜，就能看到 Issue 到底建没建出来。插件不会自动重建。

其他步骤都可以安全重试。插件启动或热重载时会恢复未结束的报障：正在等 NPC 的报障会立刻查一次评论，日志还没传完的，会提醒用户在剩余时间内重新上传。

合并转发有一种情况可能重复发送：平台已经发出去了，但插件没来得及记下来就退出了，或者等发送确认超时了。

## 日志

插件的运行日志会记录：后台轮询启动、每轮评论匹配到几条、CNB 请求失败以及转发成功。NPC 迟迟没有回复时，可以先看“编号标记匹配 N 条，可信作者匹配 N 条”这一行。标记匹配到了、作者却没匹配上，通常是 `npc_author_*` 填错了。
